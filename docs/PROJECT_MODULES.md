# Veerox AI — Module Reference

A complete, current map of every module in this repo and what it's responsible for. Generated by reading the actual code (not the original 4-day build plan in `longrunning/`, which is now historical — see that folder for original architecture decisions/tradeoffs, not current state).

**What Veerox is:** a multi-tenant SaaS where each client org gets an AI agent that handles inbound/outbound phone calls (via Plivo/Twilio + OpenAI Realtime) and WhatsApp conversations (via Meta Cloud API), backed by a shared "brain" (`core/agent.py`) that captures leads, books appointments, qualifies prospects, and hands off to humans — plus a Next.js dashboard for managing all of it (CRM, campaigns, follow-ups, team, billing/licensing).

Backend: FastAPI (`apps/api`), Postgres via SQLAlchemy async + Alembic, Redis, in-process asyncio background workers.
Frontend: Next.js App Router (`apps/web`), React Query, Tailwind.

## 1. Backend — `apps/api`

### 1.1 Routers (`apps/api/routers/`) — HTTP API surface

Wired into the app in `main.py`'s `create_app()`, each with its own router-level auth/feature-flag dependencies (no global gating at `include_router` time).

| Router | Prefix | Owns |
|---|---|---|
| `admin.py` | `/admin` | The platform/org "control plane" — the biggest router (~4100 lines): dashboard analytics, conversation review + AI summaries, full lead CRUD + import/export, voice/WhatsApp campaigns, all per-org integration settings (calling, WhatsApp, country code, OpenAI key, Plivo/Twilio/Meta credentials), scripts, qualification-criteria presets, lead-status presets, org phone numbers, Human Support claim queue, manual outbound call/WhatsApp send, and the global kill switch. |
| `appointments.py` | `/appointments` | Scheduled appointments linked to a Lead/Contact — create (conflict check, auto-creates/claims Lead, schedules reminders, sends confirmation), list, update (cancels stale reminders on reschedule/cancel), delete. Also owns the AI-requested-callback fields (`callback_at`/`callback_dispatched_at`). |
| `auth.py` | `/auth` | Token-based dashboard login (no passwords): org provisioning (platform-admin only), login (handles multi-org token disambiguation), forgot-token self-service rotation, logout, `/me`. |
| `billing.py` | `/billing` | Platform-admin org directory + manually-managed per-org licensing (no payment gateway — Razorpay was removed): list/edit/export/delete orgs, regenerate admin token, license issue/renew/extend/suspend/reactivate, platform-wide settings and social links. |
| `conversations.py` | `/conversations` | Read-only transcript access — list a user's conversations, full message history. |
| `crm.py` | `/crm` | Contacts (distinct from Leads) — **creator-siloed** address book (even admins only see contacts they created), CSV/XLSX import/export, promote-to-lead. |
| `diag.py` | `/diag` | Temporary internal latency/connectivity diagnostics for the voice/WhatsApp pipeline (marked for deletion once investigations finish); own `X-Admin-Token` check instead of the shared dependency. |
| `follow_ups.py` | `/follow-up-rules`, `/follow-up-tasks` | Automated WhatsApp/voice follow-up rule CRUD and their spawned tasks — distinct from `lead_follow_ups.py`'s manual per-lead slots. Gated per-channel (`follow_ups_voice`/`follow_ups_whatsapp`), not one flag. |
| `health.py` | `/health`, `/ready` | Liveness/readiness probes — no auth. |
| `lead_follow_ups.py` | `/lead-follow-ups` | Read-only flattened view of each Lead's 3 dated follow-up slots, for the dashboard's Follow-up Tasks page. |
| `leads.py` | `/leads` | A minimal legacy lead create/list surface — simpler/older than `admin.py`'s richer `/admin/leads`. |
| `media.py` | `/media` | Public serving of uploaded WhatsApp assets so Meta can fetch them — deliberately **no auth dependency**; secured by UUID + random access key instead. |
| `sales.py` | `/sales` | Sales/pipeline analytics derived from Lead fields (no separate Deal entity) — pipeline value by status, revenue summary, channel breakdown, qualification funnel. |
| `team.py` | `/team` | Self-service team management for the caller's own org — invite/list/update/remove members, token regeneration; enforces "at least one admin" invariant. |
| `templates.py` | `/whatsapp-templates` | WhatsApp message templates synced with Meta's Graph API — create/submit for review, sync existing WABA templates, edit/delete locally. |
| `tickets.py` | `/tickets`, `/admin/tickets` | Support tickets: org self-service raise/list, plus a separate platform-team cross-org queue (not org-scoped by design). |

**Auth model quick reference:** most routers use `verify_admin_or_session` (X-Admin-Token OR dashboard session) + `require_feature(...)` for plan gating; `billing.py`/`tickets.admin_router` use the stricter `verify_platform_admin`/`verify_platform_team_member`; `MemberScopeDep`/`AnalyticsScopeDep` restrict `role=="member"` callers to leads/appointments/conversations they've claimed.

### 1.2 Background workers (`apps/api/workers/`) — asyncio poll loops in `main.py`'s lifespan

| File | Polls for | Does |
|---|---|---|
| `campaign_dialer.py` | `CampaignTarget` rows, `status="pending"`, `channel="voice"`, on running campaigns | Claims up to remaining `max_concurrent_calls` capacity, places outbound calls via `channels/voice/failover`, pre-warms the OpenAI Realtime session. 5s interval. |
| `campaign_scheduling.py` | — (shared helper, not its own loop) | `promote_scheduled_campaigns` (scheduled→running) and `complete_finished_campaigns` (running→completed), called from both dialer and WhatsApp dispatcher each tick. |
| `follow_up_dispatcher.py` | Leads with due `follow_up_at`, active `FollowUpRule` matches, due `FollowUpTask` rows, due `Appointment.callback_at` | Materializes tasks, then sends WhatsApp/places voice calls for due tasks, **and dials due AI-requested callbacks** (added for the Call Back feature — see §3). 5s interval, batch 20. |
| `license_expiry_worker.py` | `Org` rows with `license_status="active"` past `license_expires_at` | Flips to `"expired"`. 300s interval. |
| `whatsapp_dispatcher.py` | `CampaignTarget` rows, `status="pending"`, `channel="whatsapp"`, on running campaigns | Claims (batch 10), sends template/free-text via Meta Graph API, resolves synchronously within the tick. 5s interval. |

### 1.3 Channel adapters (`apps/api/channels/`)

**`voice/`** — the calling pipeline:
- `realtime_bridge.py` — hot path: bridges Plivo/Twilio bidirectional audio WebSocket to OpenAI Realtime API.
- `adapter.py` — translates Realtime session events into turn handling; converts shared tool definitions to Realtime schemas; dispatches function calls through the shared `DISPATCH_TABLE`.
- `turn_controller.py` — live turn-taking/interruption intelligence (filler vs. real speech during agent output).
- `failover.py` — tries Plivo then Twilio to place a call, per-org credentials only.
- `plivo_client.py` / `twilio_client.py` — provider-specific call clients.
- `webhook.py` — answer webhook, detects provider, returns markup bridging to `/voice/stream`.
- `elevenlabs_client.py` — optional TTS swap-in for OpenAI's native speech.
- `language_detect.py` — best-effort caller language detection.
- `number_provider.py` — which provider a phone number belongs to.
- `org_numbers.py` — org's dedicated number CRUD + rotating/default lookups.
- `plivo_provisioning.py` — best-effort registration of inbound Answer URLs.

**`whatsapp/`**:
- `webhook.py` — Meta Cloud API webhook (GET verify handshake, POST inbound receipt), minimal work before handoff.
- `adapter.py` — bridges inbound envelope to `AgentCore` as a FastAPI BackgroundTask.
- `client.py` — outbound + media send client (Graph API).
- `webhook_registration.py` — best-effort programmatic webhook/subscription registration.

**`email/`**:
- `brevo_client.py` — transactional email via Brevo API.
- `templates.py` — HTML/text bodies for Veerox's own transactional emails.

### 1.4 Core shared logic (`apps/api/core/`)

| File | Responsibility |
|---|---|
| `agent.py` | `AgentCore` — the channel-agnostic "brain"; only module that knows prompts/tools/LLM/turn persistence. Voice/WhatsApp adapters call `handle_turn` and never reach past it. |
| `tools.py` | Agent tool schemas + handler implementations: `capture_lead`, `book_appointment`, `request_callback`, `transfer_to_human`, `qualify_lead`, `mark_not_interested`, `lookup_customer`, WhatsApp sends, `initiate_ai_call`. |
| `prompts.py` | Base system prompt(s), timezone-aware defaults (Asia/Kolkata). |
| `llm.py` | OpenAI chat-completions wrapper → local `ChatResult`/`ToolCall` dataclasses (keeps agent layer SDK-agnostic). |
| `memory.py` | Loads/persists conversation history with message-count + token-budget caps. |
| `org_credentials.py` | Resolves per-org Plivo/Twilio/Meta credentials (no platform fallback except the platform's own owner org). |
| `org_openai_key.py` | Resolves which OpenAI key to use per org (own key, else platform shared key). |
| `org_social_links.py` | Platform-wide social/contact links prompt helper. |
| `phone.py` | Org-aware phone normalization (default country code). |
| `security.py` | Login token generation/hashing for `AccountUser` (SHA-256, admin-provisioned accounts). |
| `sessions.py` | Server-side dashboard sessions in Redis (chosen over JWT for instant revocation). |
| `crypto.py` | Fernet symmetric encryption for server-decryptable secrets (e.g. per-org OpenAI keys). |
| `transcribe.py` | Whisper-based audio transcription, shared across voice + WhatsApp voice notes. |
| `whatsapp_assets.py` | Org WhatsApp media library lookups for `send_whatsapp_file` + prompts. |
| `whatsapp_template_catalog.py` | Org approved-template lookups for `send_whatsapp_template` + prompts. |

### 1.5 DB models (`apps/api/db/models/`)

| Model | Represents |
|---|---|
| `Org` | Tenant/client org — `license_status` (active/suspended/expired), `enabled_features` JSON gate, encrypted per-org credentials. |
| `AccountUser` / `OrgMembership` | Dashboard login identity + its role (admin/member) within an org — distinct from `User`. |
| `User` | Per-channel messaging identity (WhatsApp/voice contact), keyed by phone, unique per (org, phone). |
| `Contact` | Unified CRM entity a rep manages across channels, creator-siloed. |
| `Lead` | A qualified/tracked prospect, unique per (org, user); `status` + independent `qualification_status`; up to 3 follow-up slots. |
| `LeadStatusPreset` | Org-custom pipeline stage layered onto built-in Lead statuses. |
| `Conversation` / `Message` | One call/WhatsApp session and its individual turns; `Conversation.summary` is AI-generated on demand. |
| `Appointment` | Scheduled meeting tied to a Lead/Contact; `status` (scheduled/confirmed/completed/cancelled/no_show); separate `callback_at`/`callback_dispatched_at` pair for AI-requested callbacks (see §3). |
| `CallCampaign` / `CampaignTarget` | Outbound voice/WhatsApp outreach campaign and its per-prospect targets. |
| `FollowUpRule` / `FollowUpTask` | Standing automated follow-up rule and its materialized scheduled sends. |
| `Script` | Named AI system-prompt script assignable per campaign or as channel default. |
| `QualificationCriteriaPreset` | Reusable qualification-bar text for campaigns. |
| `OrgPhoneNumber` | One dedicated Plivo/Twilio/WhatsApp number owned by an org, with rotation order. |
| `WhatsAppTemplate` | Saved Meta-approved template. |
| `WhatsAppAsset` | Uploaded file the WhatsApp agent can send; access-key gated. |
| `SupportTicket` | Client-submitted ticket routed to the Veerox platform team. |
| `UsageCounter` | Monthly per-org usage counter for plan-limit checks. |
| `PlatformSettings` | Singleton platform-wide settings row. |

### 1.6 Schemas (`apps/api/schemas/`)

Pydantic request/response shapes, one file per domain, mirroring the routers above 1:1 (`appointment.py`, `lead.py`, `crm.py`, `campaign.py`, `follow_up.py`, `conversation.py`, `sales.py`, `reports.py`, `team.py`, `template.py`, `support_ticket.py`, `script.py`, `whatsapp_asset.py`, `lead_status_preset.py`, `qualification_criteria_preset.py`, `org_numbers.py`, `admin.py`, `billing.py`, `auth.py`) plus `whatsapp_common.py` for a shared button-param shape reused across every WhatsApp send path.

## 2. Frontend — `apps/web/src`

### 2.1 Pages (`app/(dashboard)/`)

Grouped by area (many legacy paths are thin redirects to the current canonical route — kept for old bookmarks/links):

- **Home/dashboard:** `page.tsx` (kill switch, quick actions, analytics summary), `analytics/sales/page.tsx`.
- **CRM (canonical):** `crm/leads`, `crm/contacts`, `crm/appointments`, `crm/qualification` (→ redirects to leads).
- **Automation:** `automation/campaigns/{voice,whatsapp}`, `automation/follow-ups/{voice,whatsapp}`.
- **Calling:** `calling/` (dial + analytics), `calling/conversations`, `calling/human-support`, `calling/settings`; several `calling/*` legacy routes redirect to the unified CRM/automation pages.
- **WhatsApp:** `whatsapp/` (send + analytics), `whatsapp/conversations`, `whatsapp/human-support`, `whatsapp/media`, `whatsapp/settings`, `whatsapp/templates`.
- **Cross-channel:** `conversations/`, `human-support/`, `follow-up-tasks/`.
- **Platform-admin:** `organizations/`, `organizations/expiring/`, `support-tickets/`.
- **Org self-service:** `team/`, `settings/`, `support/`.
- **Legacy redirects:** `leads/`, `dial/`, `calling/dial`, `calling/campaigns*`, `whatsapp/leads*`, `whatsapp/send`.

### 2.2 Component directories (`components/`)

`automation/`, `calling/`, `campaigns/`, `conversations/`, `crm/`, `dashboard/`, `follow-up-tasks/`, `human-support/`, `leads/`, `organizations/`, `reports/`, `settings/`, `team/`, `tickets/`, `whatsapp/` — each domain's dialogs/tables/badges. `layout/` holds app shell chrome (shell, page header, topbar, query boundary, tabs). `onboarding/` holds the product tour. `ui/` holds generic design-system primitives (button, card, badge, dialog, input, select, table, toast, pagination, etc.), shared across everything.

### 2.3 `lib/`

`api.ts` (fetch wrapper + auth headers), `auth-context.tsx` (session context), `types.ts` (shared TS types), `format.ts` (date/number formatting), `query.ts` (React Query setup), `orgFeatures.ts` (feature-flag helpers), `phone.ts`, `license-expiry.ts`, `social-links.ts`, `chart-colors.ts`, `download-csv.ts`, `utils.ts`, plus `onboarding/` (tour helpers).

### 2.4 `lib/hooks/`

One React Query hook file per resource, thin wrappers over `api.ts`: `useAppointments`, `useLeads`, `useContacts`, `useCampaigns`, `useConversations`, `useFollowUps`, `useLeadFollowUps`, `useHumanSupport`, `useTeam`, `useTemplates`, `useTickets`, `useWhatsappAssets`, `useScripts`, `useSocialLinks`, `useOrgNumbers`, `useOrgCountryCode`, `useLeadStatusPresets`, `useQualificationCriteriaPresets`, `useAdminOrgs`, `useAdminSettings`, `useAuthApi`, `useOutbound`, `useKillSwitch`, `useStats`, `useReports`, `useSales`, `useConfig`, plus `useClientPagination` (generic pagination) and `index.ts` (barrel export).

## 3. Recent addition: AI-requested callbacks (Sept 2026)

Worth calling out since it touches several layers above: when a caller says "I'm busy, call me back later," the `request_callback` tool (`core/tools.py`) logs an `Appointment` row with `callback_at` set (shown as the **Call Back** column on `/crm/appointments`, no separate "When" column). `workers/follow_up_dispatcher.py` then polls for due, undispatched callbacks (`callback_dispatched_at IS NULL`) and places the actual outbound call the same way an automated follow-up call goes out. Editing `callback_at` from the dashboard re-arms dispatch. Two migrations: `b1c2d3e4f5a6` (adds `callback_at`) and `d3e4f5a6b7c8` (adds `callback_dispatched_at`).
